Solana in one analogy: a shared spreadsheet with strict row permissions

Accounts are the rows

A wallet is not a bag containing every token. A mint account defines a token. A token account holds one owner's balance of one mint. An ATA is the predictable default row for an owner+mint pair.

Programs are the formulas

Programs are stateless code. They do not “own” your business state; separate accounts do. A transaction names every row the formula may read/write. The runtime can then parallelize non-conflicting work.

transaction = instructions + account metas + signatures success = every instruction succeeds failure = all state changes roll back

PDAs are numbered lockers

A PDA has no private key. It is derived from seeds and a program ID. The program can sign for it with the same seeds. That is why an escrow vault can release tokens only through program logic.

escrow = findPDA(["escrow", maker, seed]) vault = ATA(owner = escrow, mint = tokenA)

CPIs are asking another clerk

Your program can call System, Token, or Associated Token programs. A user signs for their own funds; a PDA signs with invoke_signed. Always ask: who is the authority?

Who signs to release Token A from an escrow vault?

Write the state machine: allowed states and transitions.
List every account, signer, writable flag, owner, PDA seed.
Define conservation rules: what can increase, decrease, or move?
Name failure cases before happy paths.

After editing code

Format and lint.
Run LiteSVM tests against compiled SBF.
Simulate before broadcasting.

Every terminal transition must make reuse impossible. “Double take” should fail because the escrow account is gone.

Account checklist

#[account( mut, has_one = maker, seeds = [b"escrow", maker, seed], bump = escrow.bump, close = maker )] pub escrow: Account<'info, Escrow>;

Anchor constraints are executable documentation. They reject malformed account graphs before your business logic runs.

LiteSVM is a microscope

It runs an in-process SVM quickly. Load your compiled .so, create mints/ATAs, send signed transactions, inspect account bytes and balances. It is not a fake unit test: it exercises the program in a deterministic local runtime.

anchor build cargo test --workspace --tests cargo clippy --workspace --all-targets -- -D warnings

Proof before pride

A green test is only useful when it asserts state. For escrow, assert both token balances, vault authority, mint identities, and account closure. For a vault, assert rent preservation and that unauthorized users fail.

AMMs: a vending machine that reprices itself

Unlike an order book, an AMM does not wait for a matching buyer. A pool holds two reserves. Your trade changes the ratio, and the curve quotes the next price.

Constant-product intuition

x · y = k. If you add X, the pool must reduce Y so the product stays near k. Large trades relative to the pool cause more slippage.

Try a swap

Liquidity provider

You deposit both assets, receive a share claim, and earn fees. But your withdrawal value changes with price.

Impermanent loss

If the external price moves, arbitrage rebalances your pool. You may have fewer valuable units than simply holding.

MEV + safety

Use slippage limits and deadlines. A public pending transaction can be observed and reordered.

Principles to keep

Accounts are the product. Code only defines transitions.

Authority is a graph. Every movement of value must have an explicit signer or PDA signer.

Tests are executable explanations. Assert state, not vibes.

Start local, then simulate, then send. Never debug with real money first.
